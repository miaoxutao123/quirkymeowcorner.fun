九月的某天，我在一个 Unity 项目的提交里写了这句：

```
fix(v0.5): make runtime systems truly generic
```

值得说明的是，两个月前我在 v0.2 的第一笔提交里就用了 "generic" 这个词：

```
docs: add v0.2 Generic Agent World Runtime development spec
```

同一个词，用了两次，中间隔了五个版本。也就是说，我宣布它通用之后，花了五个版本才发现它不通用。

## 为什么"通用"这个词特别容易骗人

因为它描述的是一个否定性的性质：**不依赖具体实例**。而"不依赖"这件事，你只能靠穷举来证明——你把所有具体实例都试一遍，都不出问题，才算。

这和"快"、"小"、"简单"不一样。那些有度量，能被测出来。通用没有度量，只有反例。

所以写 `generic` 的时候，我心里想的是"我抽了一层接口"，而实际上做的是"我把当前这一个实例硬编码进了一层接口里"。**接口存在不等于抽象成立。**

## 后来加的规矩

现在我的项目模板里有一行硬性要求，写在给 agent 读的工程约束文件里：

> 任何声称"通用"的设计，验收清单里必须配一个"换一个具体实例还能跑"的测试。没有这个测试的，"通用"这个词不许出现在提交信息、注释和文档里。

这条规矩的作用不是让人多写测试，是**让形容词变成可证伪的命题**。写完之后要么加测试，要么改措辞。两种结果都比原来那句 `generic` 有价值。

## 推广一下

同样的坑还有一堆近义词：

| 这类词 | 真实含义 | 验收方式 |
|---|---|---|
| 通用 | 换成别的实例还能跑 | 换一个实例跑一遍 |
| 可扩展 | 加第三个实现不用改老代码 | 真的加第三个 |
| 幂等 | 重复执行结果不变 | 连跑两次比对 |
| 容错 | 上游挂了还能降级 | 断网试一次 |
| 高性能 | 在这组约束下够快 | 给出数字和场景 |

这五个词的共同点是：**它们都是关于"当情况变化时会发生什么"的断言，而当前状态的测试全都证明不了它们。**

## 一点自我提醒

我写这些的时候，正在给另一个项目做类似的架构。这次的做法是：先写一个"第二个实例"，用最小的方式接进去，跑通了再回头抽接口。

顺序反过来——先抽接口再想第二个实例长什么样——那五个版本的弯路大概还会再走一遍。
