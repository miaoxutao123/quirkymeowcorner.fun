这是本站的第一个作品，也是本站所有文章的数据来源。

## 它解决什么问题

我想写博客，但每次打开编辑器就想不起来前几天做了什么。翻聊天记录太碎，翻 git log 太细，翻 GitHub 主页又看不到私有仓库。

于是有了这个东西：把散在各处的痕迹合并成一份日历，点某一天，直接看到当天做了什么、写了哪些代码、和 agent 讨论过什么。

## 数据从哪来

四路信号，全部本地采集：

| 来源 | 采到什么 | 规模 |
|---|---|---|
| GitHub 全部仓库 | 提交记录 | 47 个仓库，本人 319 次提交 |
| 本地项目目录 | 文件改动 | 16150 个有意义改动，58 天 |
| Agent 会话 | 对话轮次 | 六平台，清洗后 134 条真实表达 |
| 仓库元信息 | 私有/公开 | 私有占比 78.7% |

## 三个差点算错的地方

这部分比结果重要。

**一、fork 仓库里别人的提交不是你的。**

第一次跑出 4323 次提交，我以为自己四个月写了一千多笔，兴奋了半分钟。实际上 fork 的仓库里带着上游作者的全部历史——AstrBot 光上游就有 1896 次。按 `author.login` 过滤后，属于我的只有 319 次。

**二、clone 来的 SDK 不是你的产出。**

本地扫文件时算出 55824 个改动，数字大得可疑。查下来是把 `esp-idf`（clone 的 ESP32 SDK）和供应商固件当成自己的项目在数。规则改成：**跳过任何含 `.git` 的子目录**，因为那是独立仓库，不是我的代码。数字降到 16150。

**三、文件数不能线性计分。**

有一次批量操作生成了两万多个文件，直接刷出 1221 分，把真正有内容的日期全盖住了。改成每个项目单日封顶 4 分（`min(files/20, 4)`）——一个批量操作仍然只是「一件事」。

## 还发现了一件事

GitHub 主页的贡献日历显示我今年有 56 次提交、33 个活跃日。

实际是 319 次提交、114 个活跃日。

差别全在私有仓库。2026 年 9 月单月我推了 145 次提交，主页上显示是零。这不是 GitHub 的问题，图本来就是给公开贡献用的。但它确实造成了一个错觉：**看起来什么都没做，实际上一直在做**。

这个博客的一个用途就是修正这个错觉。

## 技术选择

零第三方依赖，全部标准库：

- 采集用 `gh api` + `os.walk`
- 合并打分用纯 Python
- 展示层是单个 HTML 文件，数据内嵌

没引数据库，没引前端框架。理由很简单——这些东西如果坏了，我希望自己能修。前两次博客都是死在别人的插件上。
